## Why

`core-output-language` currently has exactly one resolution mode: a single global env var (`SIGNAL_OUTPUT_LANG`) applied per-agent as on/off. That mode is correct for info-radar (one operator-wide reading-language preference) but wrong for knowledge ingestion, which reuses the *same* global setting to force frontmatter `title`/`summary` into the operator's preferred language even when it should instead preserve the archived source's own language — the opposite of what a long-term archive is for. It also has no mechanism for a user to change the preference at runtime (env vars are fixed for a container's lifetime), and info-radar's `title` field bypasses the LLM entirely today, so it stays in the source language while `summary`/`impact` are translated — inconsistent output on the same dashboard card.

This change generalizes the existing (already-measured, already-working) language-injection mechanism from "one env var, one mode" into a small per-agent policy model, and gives the dashboard a real way to drive it live.

## What Changes

- Generalize `extra.output_language` from a bool to a policy: `off` | `global` | `same_as_source` | `fixed:<lang>`. The injection mechanism itself (unconditional rule phrasing, `{{OUTPUT_LANGUAGE}}` token substitution, class-based field wording) is unchanged — only the source of the resolved language value generalizes.
- **BREAKING**: Retire `SIGNAL_OUTPUT_LANG` from the resolution path. The `global` policy now resolves from a runtime state file (`~/.next-signal/language.json`), falling back to a hardcoded `"en"` constant in code — never from `.env`.
- Add a dashboard-writable live preference: the existing locale-toggle action (which already sets the `paca_locale` cookie) also writes the state file in the same action. A one-time process-start hook seeds the file if it's missing.
- info-radar: `radar_tier2_impact` gains a `title` field so title is generated by the LLM alongside `summary`/`impact`, all under the same `global` resolution — closing the gap where title alone bypassed the LLM. `radar_analyses` gains a `title` column; the dashboard reads it from there instead of `radar_items.title`.
- Knowledge ingestion: `knowledge_artifact_editor`, `knowledge_github_cleaner`, `knowledge_frontmatter`, `knowledge_github_summary` move from the global setting (frontmatter agents) or no rule at all (cleaning agents) onto `same_as_source`, driven by a new deterministic, non-LLM language-detection step run once per ingested item on the raw fetched content.
- `tags` are explicitly **not** part of this mechanism — they keep their existing bespoke, hardcoded-English prompt instruction, unchanged.
- Correct a spec/code drift found while tracing this: `openspec/specs/info-radar-analysis/spec.md` currently requires `radar_dedup_judge` to follow the configured output language; the shipped prompt and YAML have always exempted it (its `reason` is internal and discarded). This change updates the requirement to match what's actually shipped.

## Capabilities

### New Capabilities

(none — this generalizes existing capabilities rather than introducing a new one)

### Modified Capabilities

- `core-output-language`: replaces the single-env-var resolution model with a per-agent policy (`off` / `global` / `same_as_source` / `fixed:<lang>`), a state-file-backed live global preference with a hardcoded code default, and a deterministic source-language detection step for `same_as_source`. Retires the `SIGNAL_OUTPUT_LANG` requirement.
- `info-radar-analysis`: `radar_tier2_impact` produces `title` in addition to `summary`/`impact`, all under the `global` policy. Corrects the `radar_dedup_judge` requirement to reflect its actual (and intentional) exemption.
- `knowledge-pipeline`: frontmatter and body-cleaning agents move to the `same_as_source` policy, replacing "follow the global setting" (frontmatter) and "exempt, no rule" (cleaning) with "target the detected source language, explicitly." The tag-language and general non-goal-of-translating-the-body guarantees are preserved, just re-derived from the new policy instead of a bespoke exemption.
- `dashboard-shell`: the locale-toggle action gains a second side effect (writing the content-language state file); a process-start hook seeds that file on first launch.

## Impact

- **Code**: `src/paca/core/context.py` (shrinks back to shared-context only), new `src/paca/core/language.py` (policy resolver, live-preference read/write) and `src/paca/core/language_detect.py` (swappable detection interface, Unicode-script-ratio heuristic as the first implementation), `src/paca/agents/loader.py` (`build_from_name`/`_compose_instructions` gain a per-call language override), `src/paca/workflows/info_radar_analysis/{schemas.py,stages/tier2.py,store.py}`, `src/paca/workflows/stages/knowledge_ingest/{fetch.py,artifact_editor.py}`, `scripts/bootstrap_db.py` (new `radar_analyses.title` column).
- **Config**: `configs/agents/{radar_tier1_filter,radar_tier2_impact,radar_recap,radar_dedup_judge,knowledge_artifact_editor,knowledge_github_cleaner,knowledge_frontmatter,knowledge_github_summary}.yaml` — `extra.output_language` values updated to the new policy strings.
- **Dashboard**: `dashboard/instrumentation.ts` (new), the existing locale-toggle server action (extended), `dashboard/lib/radar/queries.ts` (title read from `radar_analyses` instead of `radar_items`).
- **Deployment**: `.env.example` loses `SIGNAL_OUTPUT_LANG`; `docs/` (bilingual) gains documentation of the new state file and policy model, replacing the env-var docs.
- **Specs**: amends `openspec/specs/core-output-language/spec.md`, `openspec/specs/info-radar-analysis/spec.md`, `openspec/specs/knowledge-pipeline/spec.md`, `openspec/specs/dashboard-shell/spec.md`.
